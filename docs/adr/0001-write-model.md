# 0001. Модель записи рабочего пространства

## Контекст

Клиент сохраняет рабочее пространство целиком: `POST /api/workspace` присылает все карточки, шаги, цели, ЛПР и оценки, которые он видит. Сервер раньше приводил таблицы к этому снимку: строки из тела записывал, а строки базы, которых в теле нет, удалял.

Это теряет данные при параллельной работе. Устаревшая вкладка лида не знает о карточке, которую сотрудник добавил позже, и при сохранении удаляет её без единого сообщения об ошибке. Путь записи читал базу, потом писал её без блокировок, поэтому параллельная смена пароля, свежий вход (сессия) или чужая новая строка тоже затирались старым снимком. Запись переписывала таблицы целиком, из-за чего накапливались мёртвые версии строк и сбрасывались `created_at`.

Правильный долгосрочный ответ - гранулярные операции по сущностям (PATCH и POST отдельных карточек, шагов, целей) вместо снимка целиком. Он меняет API и требует переписать клиентскую модель сохранения, а это решение владельца продукта.

## Решение

Оставить снимок целиком на проводе, но изменить то, как сервер его применяет. Три механизма (контракты K1 и K2 волны 2 исправлений аудита 2026-10-04):

1. **Запись разностью.** Чтение из PostgreSQL (`readDb()` в `server.js`) вешает на результат базовое состояние `snapshotRows()` из `db/repositories/workspace.js`: по каждой таблице ключ -> подпись значений колонок, посчитанная теми же функциями `value()` из `db/repositories/tables.js`, что идут в upsert. `writeDb()` передаёт его в `syncWorkspace({ base })`. С базовым состоянием пишутся только новые и изменённые строки, а удаляются только ключи, которые были в базовом состоянии и исчезли из снимка. Строки, появившиеся в базе после чтения (чужая карточка, новая сессия, свежий пароль), не затрагиваются, потому что запись просто не касается их. Базовое состояние считается один раз при чтении по сырым строкам, до нормализации. Без базового состояния (старые вызовы, file-режим) работает прежняя запись полным снимком. Базовое состояние хранится под символьным свойством результата и копируется вместе с ним при `{ ...db }`, поэтому все места вызова `writeDb` получают защиту без правок; усечённый (скоупленный) снимок базовым состоянием быть не может, его запись запрещена.
2. **`knownIds` для устаревшего клиента.** Тело запроса может нести `knownIds = { cards, actions, goals, lprs, competencyAssessments }`: id строк, которые клиент видел (получил с сервера или сам создал и успешно сохранил). При слиянии (`mergeWorkspaceUpdate`: админ и лид по всем таблицам списка, сотрудник по карточкам, шагам, целям и ЛПР - оценки компетенций он не записывает) строка базы, которой нет в теле, удаляется, только если её id есть в `knownIds` своей таблицы; иначе клиент её не видел, и она сохраняется. Если `knownIds` не прислан или поле таблицы не массив, действует прежняя семантика «нет в теле - удалено», чтобы работали старые клиенты и API-тесты. Размер входа ограничен: до 20000 id на таблицу, длина id до 200.
3. **Оптимистичная блокировка.** Версия строки карточек, шагов, целей и ЛПР - `updated_at`. Версия проверяется только у строк, которые запрос реально меняет (при записи разностью). Устаревшая версия даёт `409` с перечнем конфликтов и актуальным состоянием; счётчик `versionConflicts` в `/metrics`. Клиент показывает баннер с выбором «загрузить актуальные данные» или «перезаписать моими» и не повторяет сохранение бесконечно.

## Последствия

- Потеря чужих строк при сохранении устаревшей вкладкой и откат паролей и сессий параллельной записью устранены; зато клиент, не присылающий `knownIds`, сохраняет прежнее опасное поведение. Все клиенты нашего интерфейса его присылают.
- Гонки двух людей над одной и той же строкой по-прежнему решает оптимистичная блокировка: проигравший получает `409` и баннер. Слияния полей внутри строки нет.
- Гранулярные PATCH по сущностям не делаем сейчас. Это смена API и клиентской модели сохранения, решение за владельцем. Снимок остаётся ограничен лимитом тела запроса (1 МБ), и на очень больших командах сохранение упрётся в `413`: это известное ограничение.
- Подписи считаются теми же функциями, что и upsert, поэтому «подпись не изменилась» означает «upsert записал бы то же самое»: любое новое поле колонки таблицы должно добавляться в описание `tables.js`, иначе оно выпадет и из записи, и из сравнения.
- `pulse_history` не сверяется со снимком на удаление: снимок содержит только то, что клиент успел прочитать, и удаление «лишнего» стёрло бы историю.
