# 0005. Модель приватности: что видит участник, лид и администратор

## Контекст

Аудит 2026-10-04 (находки privacy-1…privacy-9, code-server-b-5, code-server-b-8, db-7, приложение А) показал, что продукт хранит данные трёх уровней чувствительности и по-разному их защищает:

- оценочные тексты лида о человеке (`performanceNarrative`, `growthNarrative`) и черновые оценки компетенций уходили участнику в ответе `GET`/`POST /api/workspace`: `person` отдавался целиком;
- анонимные опросы: порог ответов применялся только к опросу в целом, а не к отдельному вопросу, и его можно было снизить до 2; необязательный вопрос с одним ответом раскрывал ответ одного человека;
- приватные заметки лида принадлежали человеку, а не автору: любой лид скоупа (и любой следующий) читал и удалял заметки коллег;
- постоянное удаление человека оставляло его именные ответы на опросы;
- удаление лида-владельца опроса переводило опрос в ветку «без владельца», и он становился доступен всей организации;
- журнала действий над учётками, людьми и приватными данными не было.

Владелец поручил принять решения по приватности самостоятельно; эта запись фиксирует принятые решения и то, что осознанно осталось. Токены сессий вынесены в отдельный [ADR 0006](0006-session-tokens-hashed.md).

## Решение

**Оценочные тексты и компетенции (D1).** Сервер вырезает из `people[]` поля `performanceNarrative` и `growthNarrative` для участника и демо-пользователя (`scopeWorkspace`). Админ и лид получают их как раньше. Остальные поля person не трогаются, в том числе `managerFocus`: он показывается в общем виде встречи. Из `competencyAssessments` участник видит только записи со `status === "validated"`, лид и админ - все. Фильтрация серверная, интерфейс ничего не решает.

**Анонимные опросы (D2).**

- Порог ответов не ниже 3: при сохранении `anonymousMinResponses` ограничивается диапазоном 3..10, при чтении эффективный порог - `Math.max(3, anonymousMinResponses || 3)`, в том числе для уже сохранённых опросов с порогом 2.
- Агрегат вопроса любого типа (шкала, один выбор, несколько вариантов, текст, дата) показывается, только если на этот вопрос ответило не меньше порога респондентов. Иначе `perQuestion[id] = { count, hidden: true, minResponses }` без распределения, среднего и сэмплов; клиент показывает «Недостаточно ответов для показа этого вопроса (нужно не меньше N)».
- Общий скрытый агрегат (всего ответов меньше порога) сохраняется.
- Анонимные текстовые ответы и даты по-прежнему затираются в агрегатах и CSV.

**Приватные заметки лида (D3).** Заметка помнит автора: `manager_notes.author_user_id` (миграция `0027_manager_notes_author.sql`, `on delete set null`), в объекте - `authorUserId`. `platform_admin` видит заметки всех людей своего скоупа. Обычный лид видит заметки, где `authorUserId` равен его id, или у которых автора нет: старые заметки без автора считаются общими для лидов скоупа, как было до миграции (backfill не делался, угадывать автора нельзя). Удалить заметку может автор, `platform_admin`, а заметку без автора - любой лид скоупа. Во всех остальных случаях ответ `404 «Заметка не найдена»`: существование чужой заметки не раскрывается.

**Постоянное удаление человека (D4).** `DELETE /api/people/:id?permanent=1` удаляет и именные ответы на опросы (`survey_responses.person_id`). Анонимные ответы не связаны с `person_id` (только серверный хэш), их удаление не затрагивает.

**Опрос удалённого лида (D5).** Если `ownerUserId` указан, а учётки владельца уже нет, аудитория опроса пуста; видит и управляет им только `platform_admin`. Опрос без `ownerUserId` (создан платформенным администратором, либо старые данные) работает как раньше. Чтобы это различие работало в PostgreSQL, миграция `0029_surveys_owner_without_fk.sql` снимает внешний ключ `surveys.owner_user_id` (раньше `on delete set null` обнулял владельца при удалении лида, и опрос снова открывался всей организации).

**Журнал аудита (D6).** Таблица `audit_log` (миграция `0028_audit_log.sql`, без внешних ключей: запись об удалении пользователя переживает его). Пишутся `user.create`, `user.delete`, `user.role_change`, `user.password_reset`, `user.password_change`, `person.archive`, `person.restore`, `person.delete_permanent`, `survey.delete`, `manager_note.delete`. Пароли и тексты заметок в журнал не попадают. Запись - «лучшее из возможного»: сбой журнала логируется и не отменяет основной запрос. Чтение - `GET /api/audit-log?limit=100&before=<id>` только для `platform_admin`, остальным `403`. В file-режиме журнал не ведётся.

**Не делаем в этой волне (D8).** Явная связь команды вместо свободной строки `team`; закрытие опроса и пакетное раскрытие результатов; политика хранения журнала аудита и срок хранения архива.

## Последствия

- Участник больше не видит оценочных формулировок лида о себе и непроверенных черновиков оценок. Лид, которому нужно показать участнику текст, делает это на встрече или переводит оценку в `validated`.
- Для опросов с 3-4 респондентами часть вопросов будет скрыта, пока на них не ответит достаточно людей; необязательные вопросы чаще остаются скрытыми. Это цена за то, что агрегат не раскрывает ответ одного человека.
- Лиды одного скоупа больше не видят заметок друг друга. Ранее созданные заметки остаются общими, пока их не удалят: автора задним числом не назначить.
- Ответ `404` вместо `403` на чужую заметку: чужое не отличить от несуществующего.
- Журнал растёт без ограничения: ретеншна нет (D8), чистку делает оператор вручную (см. [runbook](../runbook.md#журнал-аудита)).
- Контракт видимости по ролям, пороги анонимных опросов, заметки лида и журнал аудита проверяет `tests/api/privacy.spec.js`; случаи, требующие прямой записи в базу (опрос с порогом 2, заметка без автора, опрос с удалённым владельцем), через API не воспроизвести.

Остаточные риски (приняты осознанно):

- **Разностная атака на анонимные агрегаты.** Результаты анонимного опроса обновляются в реальном времени. Тот, кто смотрит агрегат до и после ответа одного человека (или его изменения), по разнице восстанавливает этот ответ, даже при пороге 3. Закрыть можно только закрытием опроса и раскрытием результатов пакетом (D8); пока не делаем.
- **Свободная строка `team`.** Границы команды лида определяются сопоставлением нормализованной строки `team`/`teamLabel` и явным `leadUserId`, а не связью с объектом команды. Опечатка или совпадение названий переносит человека в чужой скоуп (privacy-7). `teams` и `team_id` в схеме есть, но скоуп по ним не вычисляется.
- **`managerFocus` виден участнику.** Поле остаётся в ответе, потому что показывается в общем виде встречи; лиду не стоит писать в него оценочные формулировки.
- Архивные люди чужих команд по-прежнему видны другим лидам в части полей (privacy-4); срока хранения архива и самообслуживания данных нет.
- Администратор платформы видит все заметки скоупа и весь журнал: это доверенная роль, отдельного разделения обязанностей нет.
- Журнал содержит идентификаторы и имена: сам по себе он тоже персональные данные, а его чтение и очистка не журналируются.

## Статус
