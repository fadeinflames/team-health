# Runbook

Эксплуатация Team Health 1:1: деплой на Railway, откат, резервные копии, ротация секретов и действия при инцидентах. Всё описано по коду репозитория (`server.js`, `scripts/`, `railway.json`, `Makefile`). Чего в репозитории нет, помечено прямо.

Команды ниже даны для Windows PowerShell 5.1: по одной в блоке, без `&&`. В bash они работают так же, кроме синтаксиса переменных окружения и имени `curl.exe` (в bash это `curl`): `$env:ИМЯ = "значение"` в PowerShell соответствует `export ИМЯ="значение"` в bash. Пути с обратной косой чертой (`backups\файл.dump`) в bash пишите с прямой.

## Подготовка к работе с боевой базой

Работа с боевой базой с локальной машины идёт по её публичному адресу: внутренний хост Railway (`*.railway.internal`) снаружи недоступен. Публичный адрес и пароль берите в панели Railway у сервиса PostgreSQL (в Railway публичная строка подключения обычно лежит в переменной `DATABASE_PUBLIC_URL`, если у сервиса включён TCP-прокси; проверьте в панели). Нужны Node.js 20+, зависимости проекта (`npm ci`) и клиент PostgreSQL (`pg_dump` и `pg_restore` в `PATH`, версия не ниже серверной).

Пароль в строке подключения попадает в историю консоли. Отключите сохранение истории на время сессии:

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
```

Задайте адрес боевой базы (значение подставьте своё):

```powershell
$env:DATABASE_URL = "postgresql://пользователь:пароль@хост:порт/база"
```

Если соединение отвергается или идёт без шифрования, задайте режим SSL (те же значения, что у приложения: `require`, `verify-full`, `disable`):

```powershell
$env:DATABASE_SSL = "require"
```

**Обязательно задайте `APP_ENV=production` в том же окне.** Защиты скриптов (`migrate down` и `redo` запрещены, `seed` запрещён) определяют окружение по переменным окружения процесса, а не по адресу базы. С ноутбука `RAILWAY_ENVIRONMENT` не задан, и без этой строки `node scripts/migrate.mjs down 1` или `node scripts/seed.mjs` против боевого `DATABASE_URL` будут считать окружение локальным и выполнятся.

```powershell
$env:APP_ENV = "production"
```

Когда закончите, очистите окно от адреса базы:

```powershell
Remove-Item Env:DATABASE_URL
```

```powershell
Remove-Item Env:APP_ENV
```

## Первый деплой на существующую живую базу Railway

Когда нужен этот раздел: в базе уже есть таблицы приложения, созданные старым кодом (который сам выполнял DDL при старте), а таблицы журнала `pgmigrations` нет. Это один раз на окружение.

**Почему baseline не делается автоматически.** Это разовая операция над живой базой: она отмечает `0001`-`0016` применёнными, не выполняя их, и решение о ней должен принять человек, убедившийся, что база действительно в состоянии старого кода. Поэтому в `railway.json` baseline нет, а `migrate up` на такой базе защищён: если таблица `people` есть, а журнал `pgmigrations` пуст или отсутствует, `up` ничего не применяет, завершается с кодом 1 и печатает инструкцию. Без этой защиты `up` выполнил бы `0001`, записал её в журнал, упал бы на `0002` (таблица уже есть), и после этого `baseline` отказался бы работать из-за непустого журнала. Пропущенный шаг не портит данные: стартовая команда `npm run migrate && npm run start` не запускает приложение, а Railway перезапускает контейнер (не более 10 раз по `restartPolicyMaxRetries`) и затем останавливает деплой.

Порядок:

1. Подготовьте окно по разделу «Подготовка к работе с боевой базой» (`DATABASE_URL`, при необходимости `DATABASE_SSL`, `APP_ENV=production`).

2. Задайте в Railway Variables приложения обязательные переменные, иначе новый код не стартует: `ADMIN_PASSWORD` (не короче 12 символов, не из блок-листа) и `SURVEY_RESPONSE_SECRET` (не равен `ADMIN_PASSWORD`). Сгенерировать значение:

```powershell
node scripts/secrets.mjs generate
```

   При первом старте нового кода пароль администратора будет приведён к `ADMIN_PASSWORD` (отпечатка ещё нет), а его сессии сброшены. Старый пароль администратора по умолчанию считайте скомпрометированным: он есть в публичной истории git.

3. Убедитесь, что база в состоянии «таблицы есть, журнала нет»:

```powershell
node scripts/migrate.mjs status
```

   Ожидаемо: «Таблица pgmigrations отсутствует: база ещё не инициализирована».

4. Снимите резервную копию. Не пропускайте: это единственный способ вернуться, если что-то пойдёт не так.

```powershell
node scripts/backup.mjs dump
```

5. Проверьте копию (подставьте имя файла из вывода предыдущей команды):

```powershell
node scripts/backup.mjs verify backups\team-health-база-20261004-101500.dump
```

   Оглавление дампа не доказывает, что он восстанавливается. Для полной уверенности сделайте проверку восстановления (раздел «Резервные копии и проверка восстановления») до следующего шага.

6. Выполните baseline. Он отмечает `0001`-`0016` применёнными и по-настоящему создаёт расширение `pgcrypto` и таблицу `app_meta`, которых в старых базах нет. Таблицы приложения он не трогает.

```powershell
node scripts/migrate.mjs baseline
```

7. Убедитесь, что `0001`-`0016` отмечены, а `0017`-`0026` ожидают:

```powershell
node scripts/migrate.mjs status
```

8. Примените остальные миграции (`0017`-`0026`). Есть два способа, выберите один.

   **Способ А (рекомендуемый).** Ничего не делать руками: задеплоить новый код, и стартовая команда `npm run migrate` применит `up` перед запуском приложения. Пока шаг 8 не выполнен, старый код продолжает работать против базы после baseline без изменений.

   **Способ Б.** Применить руками, пока приложение остановлено. Не делайте этого при работающем старом коде: миграции после `0016` меняют схему (например, `0026` заменяет таблицу `pulse` представлением), и старый код с такой схемой работать не обязан.

```powershell
node scripts/migrate.mjs up
```

9. После деплоя проверьте (адрес замените на свой):

```powershell
curl.exe -s https://ваш-домен/readyz
```

   Ожидаемо `{"status":"ok","storage":"postgres"}`. Версию схемы показывает `/metrics`, поле `schema` должно быть `0026_pulse_as_view` (или новее):

```powershell
curl.exe -s https://ваш-домен/metrics
```

   Затем войдите администратором (логин `ADMIN_USERNAME`, пароль из `ADMIN_PASSWORD`).

Если `baseline` ответил, что в `pgmigrations` уже есть записи, значит его уже выполняли (или `up` успел частично выполниться): не повторяйте, а изучите `node scripts/migrate.mjs status`. Если база чистая (таблицы `people` нет), baseline не нужен, достаточно `up`.

## Обычный деплой с миграциями

Стартовая команда Railway - `npm run migrate && npm run start`: миграции применяются при каждом запуске контейнера, до старта приложения. Проверка готовности - `/readyz` (таймаут 30 с).

1. Перед деплоем с миграциями, содержащими `drop`, `alter column type` или массовое обновление данных, снимите копию и проверьте её:

```powershell
node scripts/backup.mjs dump
```

```powershell
node scripts/backup.mjs verify backups\team-health-база-20261004-101500.dump
```

2. Проверьте, что ожидает применения:

```powershell
node scripts/migrate.mjs status
```

3. Деплой: `railway up` или push в ветку, которую отслеживает Railway. Миграции выполнятся перед запуском приложения.

4. Проверьте `/readyz` (200), `/metrics` (поле `schema` равно последней миграции) и вход администратором.

Что может пойти не так на старте и как это выглядит в логах контейнера:

- «Миграции сейчас выполняет другой процесс (advisory-лок занят)» - параллельный запуск (старый и новый контейнер на момент деплоя). Код выхода 1, приложение не стартует; Railway повторит запуск, и после завершения первого процесса миграции пройдут без работы.
- «В базе уже есть таблицы приложения, но журнал миграций (pgmigrations) пуст» - нужен baseline, см. раздел выше.
- «База на миграции …, коду нужна …» или «Схема не инициализирована» - приложение стартует раньше, чем применены миграции, или в стартовой команде нет `npm run migrate`. `/readyz` в этом случае не отвечает (процесс завершился), а не отдаёт 503.

Деструктивные миграции (`drop column`, `drop table`) выполняются не в том же релизе, где код перестал использовать колонку: между ними проходит минимум один релиз и цикл копий (политика expand/contract, [ADR 0004](adr/0004-migrations-policy.md) и [migrations/README.md](../migrations/README.md)). Это и есть окно отката.

## Откат

**Код.** Откат кода - возврат на предыдущий коммит или деплой. В панели Railway: Deployments, выбрать предыдущий успешный деплой и повторить его (Redeploy). Либо `git revert` проблемного коммита и деплой. При старте старого кода стартовая команда снова выполнит `npm run migrate`; база будет новее кода, это штатная ситуация (в логе предупреждение «База новее кода»).

Откат кода безопасен, если миграции между релизами были только расширяющими (expand): старый код такую схему переносит. Если между релизами была contract-миграция (удаление колонки или таблицы, смена типа), старый код может ожидать удалённое и упасть. Тогда не откатывайте код, а чините вперёд.

**Схема.** Откат схемы на проде выполняется только одним из двух способов:

- **Forward fix** - новая миграция, исправляющая предыдущую (`node scripts/migrate.mjs create имя`, затем деплой). Основной способ.
- **Восстановление из резервной копии** с потерей данных за окно между копией и аварией; потерю нужно зафиксировать и сообщить пользователям.

`node scripts/migrate.mjs down` и `redo` вне `local` отказываются работать (не отключайте эту защиту; не работайте с боевой базой без `APP_ENV=production`, см. «Подготовка»). `down` не является средством восстановления после аварии: для `drop column` он теряет данные, для смены типа теряет точность, а после того как новый код записал данные в новую структуру, он не вернёт старую.

**Восстановление боевой базы из копии.** Самый безопасный путь - не перезаписывать боевую базу, а восстановить копию в новую пустую базу (новый сервис PostgreSQL в Railway), проверить и переключить на неё `DATABASE_URL` приложения. Скрипта боевого восстановления в репозитории нет (`make db-restore` работает только с локальной базой compose), используется стандартный `pg_restore`:

1. Остановите приложение (иначе оно пишет в базу во время восстановления).
2. Создайте новую пустую базу и задайте её адрес:

```powershell
$env:RESTORE_URL = "postgresql://пользователь:пароль@хост:порт/новая_база"
```

3. Восстановите (адрес базы виден в списке процессов локальной машины; на личном ноутбуке это приемлемо):

```powershell
pg_restore --no-owner --no-privileges --dbname $env:RESTORE_URL backups\team-health-база-20261004-101500.dump
```

4. Проверьте журнал миграций восстановленной базы:

```powershell
$env:DATABASE_URL = $env:RESTORE_URL
```

```powershell
node scripts/migrate.mjs status
```

5. Переключите `DATABASE_URL` приложения на новую базу, выполните деплой и проверьте `/readyz`.

## Резервные копии и проверка восстановления

Что есть в репозитории: `scripts/backup.mjs` с командами `dump`, `verify` и `restore-check`. Чего нет: расписания, хранилища вне хоста, срока хранения, шифрования и автоматической проверки восстановления в CI. Включены ли резервные копии на уровне платформы Railway, из репозитория проверить нельзя - проверьте в панели сервиса PostgreSQL и не считайте это заменой процедуре ниже, пока восстановление из них не проверено.

Когда снимать копию: перед первым деплоем на живую базу, перед каждым деплоем с миграциями `drop`, `alter column type` и массовым обновлением данных, перед ротацией `SURVEY_RESPONSE_SECRET` и перед любой ручной операцией над боевой базой. Регулярное расписание задайте снаружи (планировщик заданий на машине с доступом к базе, cron-задача в CI) - в репозитории его нет.

**Снять копию.** Подготовьте окно (`DATABASE_URL`, при необходимости `DATABASE_SSL`). Дамп пишется во временный файл и переименовывается только при успехе: оборванный дамп с именем `.dump` выглядел бы настоящей копией. Файл создаётся в `backups\` (каталог в `.gitignore`) с именем вида `team-health-<база>-<дата>.dump`, права ограничиваются владельцем.

```powershell
node scripts/backup.mjs dump
```

Другой каталог: `node scripts/backup.mjs dump --out D:\backups`. Адрес базы и пароль скрипт не печатает и не передаёт в аргументах процесса.

**Проверить оглавление.** Файл читается (`pg_restore --list`), ключевые таблицы (`users`, `people`, `cards`, `actions`, `goals`, `pgmigrations`) на месте. Это быстрая проверка; она не доказывает, что копия восстанавливается.

```powershell
node scripts/backup.mjs verify backups\team-health-база-20261004-101500.dump
```

**Проверить восстановление.** Копию, которую ни разу не восстанавливали, нельзя считать копией. Команда `restore-check` восстанавливает дамп в отдельную тестовую базу и сравнивает число строк ключевых таблиц (`users`, `people`, `cards`, `actions`, `goals`, `pgmigrations`) с содержимым дампа. Защиты: имя целевой базы обязано содержать `test`, с базой из `DATABASE_URL` команда не работает, перед восстановлением объекты в целевой базе удаляются.

Поднимите одноразовую базу (версия сервера - как у боевой; сейчас в compose используется `postgres:17-alpine`):

```powershell
docker run --rm -d --name th-restore-check -e POSTGRES_PASSWORD=restore-check-pw -e POSTGRES_DB=team_health_restore_test -p 55432:5432 postgres:17-alpine
```

Подождите несколько секунд, пока база запустится, и выполните проверку:

```powershell
node scripts/backup.mjs restore-check backups\team-health-база-20261004-101500.dump --into postgresql://postgres:restore-check-pw@127.0.0.1:55432/team_health_restore_test
```

Дополнительно убедитесь, что в восстановленной базе журнал миграций на месте и состояние понятно. Если в окне осталось `DATABASE_SSL=require` от боевой базы, для локальной одноразовой базы задайте `disable`, иначе подключение не состоится:

```powershell
$env:DATABASE_SSL = "disable"
```

```powershell
$env:DATABASE_URL = "postgresql://postgres:restore-check-pw@127.0.0.1:55432/team_health_restore_test"
```

```powershell
node scripts/migrate.mjs status
```

Уберите за собой (не забудьте вернуть `DATABASE_URL`, если он нужен для боевой базы, или очистить его):

```powershell
docker stop th-restore-check
```

Результат проверки (дата, файл, итог сравнения) стоит записать, чтобы знать, из какой копии заведомо можно восстановиться.

**Обращение с копиями.** В дампе лежат хэши паролей, `salt` и ответы опросов, поэтому он секретен как сама база: не коммитьте (`backups/` в `.gitignore`), не отправляйте по почте, при хранении вне машины шифруйте. Копию, снятую локально для проверки, удаляйте после неё.

**Локальный стек compose.** `make db-dump` и `make db-restore file=...` работают только с базой в контейнере `db` compose; `db-restore` перезаписывает базу (`pg_restore --clean`) при работающем `api`, поэтому останавливайте приложение. `make db-backup` и `make db-backup-verify file=...` - обёртки над `scripts/backup.mjs` и берут базу из `DATABASE_URL` окружения shell.

## Ротация секретов

### Пароль администратора (`ADMIN_PASSWORD`)

Приложение хранит в `app_meta` отпечаток уже применённого значения `ADMIN_PASSWORD`. Совпадает - база авторитетна, ничего не трогается. Не совпадает - значение применяется при старте, а сессии администратора сбрасываются.

**Способ 1 (на Railway, с рестартом).** Сгенерируйте значение:

```powershell
node scripts/secrets.mjs generate
```

Запишите его в Railway Variables как `ADMIN_PASSWORD` (не короче 12 символов, не равно `SURVEY_RESPONSE_SECRET`) и сделайте деплой или рестарт. В логе появится «Пароль администратора обновлён из ADMIN_PASSWORD, сброшено сессий: N».

**Способ 2 (без рестарта).** Подготовьте окно (см. «Подготовка») и укажите в нём текущее значение `ADMIN_PASSWORD`, которое сейчас задано в Railway, чтобы отпечаток остался «применённым» и рестарт не откатил новый пароль:

```powershell
$env:ADMIN_PASSWORD = "текущее значение из Railway"
```

```powershell
node scripts/admin-password.mjs rotate
```

Скрипт печатает новый пароль один раз и гасит сессии администратора. Свой пароль можно задать флагом `--password` (не короче 12 символов). После этого значение в Railway Variables остаётся прежним и устаревшим; база авторитетна, пока переменную не меняют. Если потом записать в переменную тот же новый пароль, при ближайшем старте он применится повторно и сессии администратора снова сбросятся, это безопасно. Уберите значение из окна:

```powershell
Remove-Item Env:ADMIN_PASSWORD
```

Для локального compose-стека: `make admin-password`.

Учётная запись администратора не меняется из интерфейса, пароль ей меняют только так. Всем остальным пользователям пароль сменяет администратор из интерфейса или они сами (с вводом текущего пароля).

### `SURVEY_RESPONSE_SECRET`

Секрет участвует в хэше анонимных ответов (`sha256(surveyId:userId:секрет)`). Его смена повышает «поколение» хэшей (счётчик в `app_meta`, в логе «SURVEY_RESPONSE_SECRET изменился, поколение хешей: N»). Последствия:

- старые ответы остаются в своём поколении и учитываются в агрегатах;
- дедупликация работает только внутри поколения: респондент, уже отвечавший на опрос, после смены может ответить ещё раз, и это будет новый ответ, а не обновление прежнего.

Меняйте секрет, когда он мог утечь (знание секрета и списка `userId` позволяет сопоставить анонимный ответ с автором), и вне окна активных опросов. Он не должен совпадать с `ADMIN_PASSWORD`, иначе приложение не стартует. Порядок: снять копию, сгенерировать (`node scripts/secrets.mjs generate`), записать в Railway Variables, деплой или рестарт, проверить лог на строку про новое поколение.

### Сессии

В PostgreSQL токен сессии хранится хэшем (sha256), в cookie лежит сырой токен ([ADR 0006](adr/0006-session-tokens-hashed.md)). Вход удаляет прочие сессии этого пользователя ([ADR 0002](adr/0002-single-session-per-user.md)); смена пароля гасит остальные сессии пользователя. Принудительно завершить сессии всех пользователей (например, после подозрения на утечку cookie) отдельной командой нельзя; единственный способ - SQL `delete from sessions` в psql на боевой базе. Сначала снимите копию, пользователям придётся войти заново.

### Пароль PostgreSQL на Railway

В репозитории нет процедуры, привязанной к платформе, поэтому только общий порядок: снимите копию; смените пароль пользователя в базе и обновите переменные подключения у сервиса PostgreSQL и приложения (у приложения `DATABASE_URL` обычно ссылается на переменную сервиса PostgreSQL, проверьте это в панели Railway); сделайте деплой или рестарт приложения; проверьте `/readyz`. Точные шаги смотрите в актуальной документации Railway.

## Смена пароля Postgres в compose-стеке без потери данных

**Предупреждение.** В `.env.example` и в сообщениях `scripts/secrets.mjs` стоит совет «смена `POSTGRES_PASSWORD` требует пересоздания volume: `make down-v`». Не следуйте ему, если в базе есть данные, которые нужны. `make down-v` выполняет `docker compose down -v` и удаляет volume `pgdata` со всеми данными; dev-стек и профиль `prod` compose используют один и тот же volume, поэтому пропадает вся локальная база. Так же опасен `make secrets-force`: он перегенерирует **все** секреты (включая `POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, `SURVEY_RESPONSE_SECRET`) и сам напоминает про `make down-v`.

Пароль Postgres в compose читается из `POSTGRES_PASSWORD` только при инициализации пустого volume. Поэтому достаточно сменить его в самой базе и в `.env`, пересоздав volume не нужно.

1. Снимите копию на всякий случай:

```powershell
make db-dump
```

2. Откройте psql в контейнере базы (внутри контейнера соединение по сокету доверенное, пароль не спрашивается). Пользователь и база по умолчанию `team_health`; если вы меняли `POSTGRES_USER` или `POSTGRES_DB`, подставьте свои.

```powershell
docker compose exec db psql -U team_health -d team_health
```

3. В psql задайте новый пароль интерактивно (так он не попадёт в историю команд и в логи), затем выйдите:

```text
\password team_health
```

```text
\q
```

4. Впишите новое значение в `POSTGRES_PASSWORD` в `.env` (сгенерировать: `node scripts/secrets.mjs generate`). Для строки подключения подходят значения из букв, цифр, `-` и `_`, сгенерированное `generate` такое.

5. Пересоздайте контейнеры приложения, чтобы они взяли новое значение (volume при этом не трогается):

```powershell
docker compose up -d
```

6. Проверьте, что приложение живо:

```powershell
docker compose ps
```

## После выкладки с хешированием токенов все пользователи входят заново

Версия, в которой токены сессий хранятся хэшем ([ADR 0006](adr/0006-session-tokens-hashed.md)), ищет в `sessions.id` sha256 от значения cookie, а в базе лежат сырые значения прежних сессий. Они не совпадают, поэтому после выкладки каждый пользователь, включая администратора, получит `401` на первом запросе и войдёт заново один раз. Это ожидаемо, а не сбой: предупредите команду до выкладки и не принимайте рост `401` и неудачных запросов на `/api/me` в первые минуты за инцидент. Миграции данных нет; старые строки истекут по сроку (14 дней) и удалятся при ближайших входах. Если нужно убрать их сразу, `delete from sessions` (сначала копия).

Откат на прежнюю версию кода тоже разлогинит всех: новые сессии в базе хэшированы и прежнему коду не подойдут.

## Журнал аудита

Миграция `0028_audit_log.sql` создаёт таблицу `audit_log`; события пишет `server.js`. Читает журнал только администратор платформы:

```
GET /api/audit-log?limit=100&before=<id>
```

Ответ `{ entries: [...] }`, от новых к старым; поля записи: `id`, `at`, `actorUserId`, `actorUsername`, `action`, `targetType`, `targetId`, `details`. `limit` по умолчанию 100, максимум 500; `before` - id последней записи предыдущей страницы (не число - `400`). Остальным ролям `403`. Запрос нужен с cookie администратора, отдельного интерфейса нет. Напрямую в базе: `select * from audit_log order by id desc limit 100` в psql.

**Что в журнале:** `user.create`, `user.delete`, `user.role_change` (в `details` роль до и после), `user.password_reset` (администратор сбросил чужой пароль), `user.password_change` (пользователь сменил свой), `person.archive`, `person.restore`, `person.delete_permanent`, `survey.delete`, `manager_note.delete`. Кто сделал, над чем и когда: `actorUsername` и `targetId` хранятся как текст без внешних ключей, поэтому запись переживает удалённого пользователя или человека.

**Чего в журнале нет:** паролей и их хэшей, текстов приватных заметок, ответов опросов, чтений (кто что смотрел), входов и неудачных входов, создания и правок карточек, целей и самих опросов. Журнал не является полным контролем доступа: он отвечает на вопрос «кто удалил или повысил».

**Оговорки.**

- Запись делается после успешной операции и «по возможности»: если журнал недоступен, в логе контейнера появится «Не удалось записать в журнал аудита (<действие>)», а действие всё равно выполнено. Отсутствие записи не доказывает, что действия не было.
- В file-режиме журнала нет, эндпоинт отдаёт пустой список.
- Ретеншна нет: таблица растёт неограниченно. Политика хранения не принята ([ADR 0005](adr/0005-privacy-model.md), решение D8). Чистить вручную, после копии, например `delete from audit_log where at < now() - interval '2 years'`; срок решает владелец.
- Журнал сам содержит имена и идентификаторы, то есть персональные данные; бэкапы с ним храните так же строго, как бэкапы базы.

## Диагностика: 503 на /readyz

Сначала определите, что именно отвечает. Три эндпоинта различаются: `/healthz` - процесс жив, `/readyz` - хранилище отвечает, `/metrics` - счётчики.

```powershell
curl.exe -i https://ваш-домен/readyz
```

```powershell
curl.exe -s https://ваш-домен/healthz
```

```powershell
curl.exe -s https://ваш-домен/metrics
```

| Что видите | Что это значит | Что делать |
|---|---|---|
| `/readyz` 503, `{"status":"unavailable","storage":"postgres"}`, `/healthz` 200 | Запрос `SELECT 1` к хранилищу не прошёл (база недоступна, исчерпан пул, сеть, неверный `DATABASE_URL` после смены пароля) | Проверьте состояние сервиса PostgreSQL в панели Railway, `DATABASE_URL` приложения и логи приложения (причина печатается ошибкой на каждый такой запрос). В `/metrics` смотрите `pool`: `waiting` больше нуля при исчерпанном `total` указывает на пул; рост `DATABASE_POOL_MAX` ничего не даст, если база недоступна |
| `/readyz` 503, `{"status":"shutting_down"}` | Процесс получил `SIGTERM` (деплой, рестарт, остановка платформой) и выводит себя из ротации; `/healthz` при этом остаётся 200 | Подождите: пауза `SHUTDOWN_DRAIN_MS` (3 с в production) и завершение запросов укладываются в общий бюджет `SHUTDOWN_TIMEOUT_MS` (10 с по умолчанию; пауза не длиннее его половины), затем процесс выходит. Если новый контейнер так и не поднялся, смотрите логи его старта |
| `/readyz` не отвечает вообще (ошибка соединения, 502 от балансировщика), `/healthz` тоже | Процесс не запущен или не стартовал | Логи контейнера, строка с причиной (см. ниже) |
| `/readyz` 503 в file-режиме | Файл `workspace.json` в `DATA_DIR` отсутствует | Режим file в production возможен только при `ALLOW_FILE_STORAGE=1` и данные не переживают контейнер; проверьте `DATABASE_URL` |

Схема старше кода (`/readyz` 503 не будет: процесс просто не стартует). Причины, которые печатает сам сервер при завершении, и действия:

- «База на миграции X, коду нужна Y. Выполните `npm run migrate`» - не применены миграции: проверьте `node scripts/migrate.mjs status` и стартовую команду (`npm run migrate && npm run start`);
- «Схема не инициализирована: таблицы pgmigrations нет» - для базы, созданной до перехода на миграции, сначала `baseline` (раздел «Первый деплой»);
- «ADMIN_PASSWORD обязателен вне local», «ADMIN_PASSWORD короче 12 символов», «SURVEY_RESPONSE_SECRET …», «DATABASE_URL обязателен вне local» - не заданы или некорректны переменные окружения;
- сообщение `migrate`: «Миграции сейчас выполняет другой процесс» - параллельный запуск, повторите позже.

Деплой, у которого `/readyz` не становится 200 за таймаут (30 с), Railway считает неуспешным и не переключает на него трафик.

## Диагностика: растут versionConflicts

`versionConflicts` в `/metrics` - число ответов `409` на `POST /api/workspace` с момента старта процесса (при рестарте обнуляется). Это не ошибка сервера: так оптимистичная блокировка сообщает, что строку (карточку, шаг, цель, ЛПР), которую пользователь пытался сохранить, кто-то изменил раньше. Пользователь при этом видит баннер конфликта и выбирает: загрузить актуальные данные или перезаписать своими.

```powershell
curl.exe -s https://ваш-домен/metrics
```

Единичные конфликты при одновременной работе нескольких людей над одним человеком в 1:1 - нормальная жизнь. Что смотреть при заметном росте:

1. Логи приложения: на каждый конфликт сервер пишет строку «Конфликт версий при сохранении: таблица:id, …». Повторяющийся один и тот же `id` в течение долгого времени означает, что пользователь не разрешает баннер (или открыта устаревшая вкладка), а не массовую гонку.
2. Устаревший клиент. Вкладка со старым бандлом, открытая до деплоя, не разрешает конфликт так, как новая: попросите обновить страницу. После выкладки нового клиента закэшированный бандл мог остаться у пользователей.
3. Одновременная правка большим числом людей одной сущности (общая карточка повестки между встречами): ожидаемо, это поведение блокировки, а не поломка.
4. Нагрузка на пул (`pool.waiting` в `/metrics`) вместе с конфликтами: долгие записи удлиняют окно гонки.

Порогов «нормы» в проекте не задано; ориентируйтесь на динамику: резкий рост после деплоя - повод проверить клиент (не зациклился ли он, не потерял ли `updatedAt` у строки) и логи с конкретными `id`. Сам по себе конфликт данные не теряет: правки пользователя остаются у него в интерфейсе до его решения в баннере.
