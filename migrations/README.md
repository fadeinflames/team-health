# Миграции

Схемой базы управляют файлы в этом каталоге, и только они. Приложение не выполняет DDL ни при каких обстоятельствах — оно лишь проверяет при старте, что база не старше кода.

До перехода на миграции схему создавал строковый литерал внутри `server.js`, исполнявшийся целиком при каждом старте процесса. Оттуда же родом комментарий про «phantom 401s»: `do $$` блок брал `ACCESS EXCLUSIVE` на `users` на каждом запуске, и записи, попавшие в ту же транзакцию, могли откатиться так, что снаружи это выглядело случайным разлогином. Это и есть причина, по которой DDL больше никогда не возвращается в путь старта.

## Быстрый старт

```
make migrate            # применить всё, что не применено
make migrate-status     # что применено, что ожидает
make migrate-new name=add_teams
make migrate-down       # откатить одну последнюю, только local
```

Напрямую, без docker:

```
DATABASE_URL=postgres://... node scripts/migrate.mjs up
```

## Именование и раскладка

`NNNN_snake_case_description.sql`, номер монотонный четырёхзначный, без дыр. Не даты: при работе вдвоём даты дают ложное ощущение порядка, а конфликт номеров при слиянии веток — ровно тот сигнал, который нужен.

Один файл — одно логическое изменение. «Добавил колонку и заодно поправил индекс в другой таблице» разносим на два файла. Единственное зафиксированное отступление — `0006_meeting_state.sql`, где четыре таблицы 1:1 с `people` описаны вместе; причина записана в самом файле.

Формат:

```sql
-- Up Migration
alter table actions add column due_at date;

-- Down Migration
alter table actions drop column due_at;
```

Журнал применённых миграций — таблица `pgmigrations` в схеме `public`. Имя дефолтное, переименовывать не надо.

## Правила

**Транзакционность.** В PostgreSQL DDL транзакционный, и каждая миграция выполняется в своей транзакции (`--no-single-transaction` в обёртке). Общая транзакция на весь прогон не годится: `set local lock_timeout` из одного файла протёк бы во все следующие, а упавшая двадцатая миграция откатила бы семнадцатую, которая отработала нормально.

`create index concurrently` и `alter type ... add value` в транзакции невозможны. Для них — отдельный файл `NNNN_name.js` вместо `.sql`:

```js
export const up = (pgm) => {
  pgm.noTransaction();
  pgm.sql("create index concurrently cards_updated_at_idx on cards(updated_at)");
};
```

Это единственный случай, когда JS-миграция допустима помимо перекладки данных, невыразимой в SQL. Причину пишем комментарием в файле.

**Локи.** В начале каждой миграции, трогающей существующую таблицу:

```sql
set local lock_timeout = '3s';
set local statement_timeout = '60s';
```

Лучше упасть за три секунды, чем встать в очередь за длинным запросом и выстроить за собой всю нагрузку. Упавшую миграцию перезапускаем, это дёшево.

**Что переписывает таблицу.** Помечаем комментарием, если операция берёт `ACCESS EXCLUSIVE` надолго:

- `add column` без `default` или с не-volatile выражением в `default` — метаданные, дёшево (PG 11+). `now()` сюда попадает: она стабильна и вычисляется один раз на весь `alter`;
- `add column` с volatile-выражением в `default` — переписывает таблицу;
- `alter column type` — переписывает, кроме расширяющих преобразований вроде `varchar(50)` → `varchar(100)`;
- `add constraint check` / `foreign key` — валидирует таблицу целиком. Делаем в два шага: `add constraint ... not valid`, затем `validate constraint` (берёт слабый лок). На больших таблицах — разными миграциями, иначе выигрыша нет: транзакция всё равно держит лок до конца;
- `create index` — блокирует запись. На боевых таблицах только `create index concurrently`, и обязательно с последующей проверкой `indisvalid`: упавший concurrently-индекс остаётся в базе невалидным.

**Запрещено:**

- вставка бизнес-данных и демо-фикстур — для этого есть `scripts/seed.mjs`;
- `if not exists` в новых миграциях. Он маскирует расхождение состояния. Идемпотентность обеспечивает журнал, а не SQL. Исключение — `0001_extensions.sql`, где это часть контракта `create extension`;
- `do $$` блоки, ищущие объекты по `like '%...%'`. Ровно этот приём в старом литерале дропал все констрейнты `users`, чьё определение содержит подстроку `role`;
- любые операции с зависимостью от того, «а вдруг колонка уже есть».

**Data-миграции.** Массовое обновление строк идёт отдельным файлом от DDL, если только новое ограничение не требует, чтобы данные были приведены в порядок раньше него (`0017_users_role_legacy_cleanup.sql` — как раз такой случай, причина записана в файле). Для по-настоящему больших таблиц — цикл по `id` с коммитом каждые N тысяч строк, в `no-transaction` файле.

**Expand / contract.** Любое изменение, ломающее работающий код, разбивается на три шага в трёх релизах:

1. *Expand* — добавить новое, оставив старое. Новая колонка nullable, двойная запись в коде.
2. *Deploy* — выкатить код, который пишет и читает новое, но терпит отсутствие старого.
3. *Contract* — отдельной миграцией удалить старое, когда все реплики обновлены.

Деплой rolling, и две версии кода какое-то время работают против одной базы, поэтому шаг нельзя пропустить. Файлы с суффиксом `_expand` в этом каталоге ждут своих contract-миграций: `0021`, `0022`, `0023`, `0024`.

## Политика отката

`down` пишем всегда, но **средством восстановления после аварии он не является**. `down` для `drop column` теряет данные; `down` для смены типа теряет точность; `down` после того, как новый код успел записать данные в новую структуру, не восстановит старую. Смотрите `0017_users_role_legacy_cleanup.sql`: его `down` честно признаётся, что не может отличить бывшего легаси-админа от изначального `platform_admin`.

Поэтому:

- `down` нужен для локального цикла разработки и для теста «down/up последней миграции» в CI;
- на проде откат схемы — только восстановление из бэкапа, с фиксацией потери данных за окно. `scripts/migrate.mjs down` вне `local` отказывается работать;
- основной способ починки — forward fix: новая миграция, исправляющая предыдущую;
- деструктивные операции (`drop column`, `drop table`) не выполняются в том же релизе, где перестали использоваться. Между «код больше не читает колонку» и «колонка удалена» проходит минимум один релиз, а лучше цикл бэкапа. Это встроенное окно отката без всяких `down`;
- перед любой миграцией с `drop` или `alter column type` — свежий `make db-dump`.

## Существующая база: baseline

У upstream и на Railway база уже живая, и пересоздавать её нельзя. Старый литерал был сходящимся (`create table if not exists` плюс `alter ... if not exists` плюс `do $$` блок, приводивший `users_role_check` к финальному виду), поэтому все базы, стартовавшие с актуальным кодом, находятся в одном и том же состоянии. `0001`–`0016` описывают ровно это состояние, написанные вручную — чтобы совпали не только колонки, но и имена констрейнтов и индексов.

Один раз на каждое окружение (local, test, Railway):

```
DATABASE_URL=... node scripts/migrate.mjs baseline
DATABASE_URL=... node scripts/migrate.mjs up
```

`baseline` отмечает `0001`–`0016` применёнными, не выполняя их, и по-настоящему создаёт две вещи, которых в старых базах нет: расширение `pgcrypto` и таблицу `app_meta`. Команда отказывается работать, если в `pgmigrations` уже что-то есть или если база чистая — в первом случае baseline уже делали, во втором он не нужен и надо просто выполнить `up`.

Для чистых баз (тестовый профиль compose, CI) `baseline` не нужен.

## Проверка идентичности baseline

Проверено, а не предположено: чистая база, `0001`–`0016`, `pg_dump --schema-only` — и результат отличается от дампа базы, созданной старым литералом, ровно на `pgcrypto` и `app_meta`. Ни одного расхождения в колонках, их порядке, именах констрейнтов и индексов. Это самый дорогой из возможных багов в этой работе, поэтому проверка повторяется в CI на каждом PR.

## Что проверяет ревьюер

- [ ] номер следующий по порядку, без дыры и без конфликта с другой веткой;
- [ ] один файл — одно логическое изменение;
- [ ] есть `-- Down Migration`, и он действительно обратен `up` (или в комментарии написано, почему нет);
- [ ] `set local lock_timeout` в начале, если трогается существующая таблица;
- [ ] нет `if not exists`, нет `do $$` с поиском по подстроке, нет бизнес-данных;
- [ ] `add constraint` — через `not valid` + `validate`;
- [ ] `create index` на боевой таблице — `concurrently`, в отдельном `no-transaction` файле;
- [ ] изменение, ломающее работающий код, оформлено как expand, а не как «переименуем и поправим код в том же PR»;
- [ ] если есть `drop` — в описании PR указано, в каком релизе колонка перестала читаться;
- [ ] `db/schema.sql` обновлён (`make db-schema`), и в диффе видно ровно то, что делает миграция;
- [ ] `EXPECTED_SCHEMA` в `server.js` поднят, если код рассчитывает на новую миграцию.

## Дрейф

`db/schema.sql` — снимок схемы после применения всех миграций, приведённый к каноническому виду. Коммитится. CI применяет миграции к чистой базе, снимает дамп и сравнивает: разошлось — PR красный.

Отдельно `make db-drift` сравнивает `db/schema.sql` с живой базой. Расхождение означает, что схему правили руками.
