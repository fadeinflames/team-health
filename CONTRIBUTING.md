# Как участвовать в разработке

Короткий путь от клона до pull request. Подробности - в [README](README.md), [Product Handbook](docs/product-handbook.md) и [runbook](docs/runbook.md); здесь только правила, которые нужно знать до первого коммита.

## Окружение

Нужен Node.js (версия - в `package.json`, поле `engines`); Docker нужен для режима с PostgreSQL и для `make test-docker`. Два равноценных режима (подробности - в [README](README.md), раздел «Разработка»), выбирайте один, оба занимают одни и те же порты:

```bash
# на хосте, файловое хранилище, без Docker
make install
make dev     # бэкенд и фронтенд с автоперезагрузкой, UI на порту 5173

# в docker, вместе с PostgreSQL
make env     # создать .env из .env.example и сгенерировать секреты, один раз
make up      # поднять dev-стек: postgres, миграции, api, web
make seed    # залить демо-фикстуры в локальную базу, если нужны
```

`make help` показывает остальные цели. Без `DATABASE_URL` приложение работает на файловом хранилище `.data/workspace.json`; это режим локальной разработки, журнала аудита в нём нет.

## Тесты

| Что | Команда | Что нужно |
|---|---|---|
| Юнит | `npm run test:unit` | ничего |
| Интеграционные | `npm run test:integration` | `TEST_DATABASE_URL`, база с `test` в имени и применёнными миграциями |
| API | `npm run test:api` | запущенный сервер, `BASE_URL`, `ADMIN_PASSWORD` |
| Конфликт версий (UI) | `npm run test:conflict` | запущенный сервер, браузер playwright |
| Всё в docker | `make test-docker` | docker; своя база, миграции с нуля |

Интеграционные тесты выполняют `truncate`, поэтому откажутся работать с базой, в имени которой нет `test`. Никогда не направляйте `TEST_DATABASE_URL` на dev- или боевую базу. Подробности - в README, раздел «Тесты».

Менять поведение без теста не стоит: правка доступа, приватности или записи требует теста рядом (`tests/api`, `tests/integration` или `tests/unit`).

## Миграции

Схему меняют только файлы в `migrations/`, приложение DDL не выполняет. Нумерация монотонная, одна миграция - одно изменение, `down` пишется всегда, изменения, ломающие работающий код, делаются по схеме expand / deploy / contract. Правила и чек-лист - в [migrations/README.md](migrations/README.md) и [ADR 0004](docs/adr/0004-migrations-policy.md). Новая миграция: `make migrate-new name=...`; после неё обновите `EXPECTED_SCHEMA` в `server.js` и снимок `db/schema.sql` (`make db-schema`, проверка - `make db-drift`).

## Данные и приватность

Продукт хранит оценочные тексты руководителя, приватные заметки и анонимные ответы. Перед правкой, которая отдаёт или собирает такие данные, прочитайте [ADR 0005](docs/adr/0005-privacy-model.md). Коротко:

- участник и демо-пользователь не получают `performanceNarrative`, `growthNarrative` и непроверенные оценки компетенций, фильтрация идёт на сервере, а не в интерфейсе;
- анонимные агрегаты не раскрываются ниже порога ответов, анонимные ответы не связываются с пользователем;
- приватные заметки привязаны к автору, чужую заметку не раскрываем даже кодом ответа (`404`);
- в журнал аудита и в логи не попадают пароли, тексты заметок и ответы опросов.

Новое поле person, которое не должен видеть участник, добавляйте в серверную фильтрацию вместе с тестом `tests/api/privacy.spec.js`.

## Стиль

- Комментарии по-русски и объясняют, почему так сделано, а не пересказывают код.
- Без лишних абстракций: пишем в стиле окружающего кода, не добавляем слой ради слоя.
- Изменение формата или модели записи, доступа, сессий - отдельная запись в [docs/adr](docs/adr/README.md) (формат: Контекст, Решение, Последствия, Статус). Принятый ADR не переписывают, а заменяют новым.

## Секреты

Не коммитьте `.env`, дампы баз и значения паролей, токенов и секретов, в том числе в тестах и документации.

- `make secrets-check` - проверка, что в локальном `.env` нет пустых и слабых секретов (идёт автоматически перед `make up`);
- `node scripts/check-burned.mjs` - поиск в дереве значений, которые когда-то утекли (в репозитории лежат только их хэши, `lib/burned-secrets.js`);
- gitleaks в CI проверяет всю историю PR; ложное срабатывание заносится в `.gitleaksignore` с пояснением.

Если секрет всё же попал в коммит, считайте его скомпрометированным и ротируйте ([runbook](docs/runbook.md#ротация-секретов)); удаление коммита ничего не исправляет. Об уязвимостях сообщайте по [SECURITY.md](SECURITY.md), а не в публичные issue.

## Чеклист pull request

- [ ] `npm run test:unit` проходит; для затронутых слоёв прогнаны интеграционные и API-тесты (или `make test-docker`);
- [ ] `npx vite build` (`make check`) проходит, если менялся клиент;
- [ ] миграция с `down`, `EXPECTED_SCHEMA` и `db/schema.sql` обновлены, если менялась схема;
- [ ] поведение, видимое пользователю или QA, отражено в `CHANGELOG.md` и в `docs/` (handbook, qa-brief, runbook);
- [ ] приватные данные не расширяют свою аудиторию; если расширяют - есть ссылка на решение владельца или ADR;
- [ ] `make secrets-check` и `node scripts/check-burned.mjs` чисты, секретов в диффе нет.
