# Team Health 1:1

[![Ask DeepWiki](https://deepwiki.com/badge.svg)](https://deepwiki.com/fadeinflames/team-health)

Платформа для регулярной управленческой работы с командой: 1:1, развитие, цели, обратная связь, командный пульс, договоренности, матрица компетенций и следующие шаги живут в одном процессе, а не расползаются по заметкам, чатам и таблицам.

## Что уже работает

- серверная авторизация через httpOnly cookie;
- учётная запись администратора: логин `admin`, пароль генерируется `make env` и не имеет значения по умолчанию;
- демо-вход с готовым универсальным 1:1: логин из `DEMO_USERNAME` (по умолчанию `demo`), пароль из `DEMO_PASSWORD`. В docker-стеке `make env` генерирует случайный пароль и кладёт его в `.env`, учётку создаёт `make seed`. Пароль `demo` действует только там, где `DEMO_PASSWORD` не задан: file-режим без `DATABASE_URL` и тестовый профиль compose (`make test-docker`);
- постоянное боковое меню: Главная, 1:1 встречи, ЛПР, Цели, Опросы, Отчёты, Команда, Админка, Настройки;
- единый раздел администратора “Команда” с профилями участников 1:1, состоянием команды и доступами;
- добавление участников администратором и тимлидом в рамках своей команды;
- создание логинов участников с главной, из “Команды” и из админского раздела;
- доступы рабочей команды внутри “Команда”: обновление пароля и удаление не-админских логинов;
- локальный или явно разрешённый сброс демо-данных без разлогина админа;
- серверная изоляция данных: участник получает только свой профиль, темы 1:1, пульс, чек-лист и следующие шаги;
- выбор участника и отдельное рабочее пространство 1:1;
- темы повестки от участника и лида;
- фильтры по открытым темам, автору, пульсу и росту;
- интерактивный пульс 1:1: энергия, нагрузка, ясность, доверие;
- живой общий протокол встречи, который сохраняется между вкладками и попадает в итоги 1:1;
- чек-лист подготовки за 24 часа до встречи;
- приватные заметки лида;
- следующие шаги с владельцами и сроками;
- генерация кратких итогов встречи;
- ЛПР: планы развития, которые связывают темы 1:1 с целями;
- цели с прогрессом, статусом, сроком и связью с ЛПР;
- опросы команды: шаблоны, конструктор, ответы, scoped-доступ, порог анонимности, агрегаты и CSV export;
- отчёты по пульсу, темам, приоритетам, целям, действиям, балансу авторства повестки и компетенциям;
- отчёты кейс-интервью: структурированные компетенции, грейд, доказательства, рекомендации, командная матрица, CSV export и импорт зон роста в ЛПР;
- ролевая модель: админ платформы, тимлид, участник команды;
- доменные шаблоны, включая optional Ops/on-call сценарий для команд с дежурствами;
- сохранение состояния на сервере: PostgreSQL в production, локальный file fallback без `DATABASE_URL`;
- защита от потери чужих правок: запись рабочего пространства разностью, оптимистичная блокировка (при конфликте интерфейс показывает баннер, см. «Запись и конфликты»).

## Локальный запуск

```bash
npm install
npm run build
npm run start
```

Приложение откроется на `http://127.0.0.1:4173`.

Файл `.env` сам Node не читает: его подставляет docker compose. Для запуска на хосте (`npm run start`, `make dev`) переменные нужно задать в окружении процесса. Если `ADMIN_PASSWORD` не задан, в `local` пароль сгенерируется при первом запуске, будет напечатан один раз и (если `.env` есть и доступен на запись) дописан в `.env`; при следующем запуске его надо снова передать в окружение, иначе сгенерируется новый.

## Разработка

`make help` показывает все цели. Два равноценных режима, в обоих правки применяются сразу: бэкенд перезапускает `node --watch`, фронтенд обновляет vite HMR.

На хосте:

```bash
make install
make dev
```

UI на `http://127.0.0.1:5173`, API на `http://127.0.0.1:4173`. Vite проксирует `/api` на бэкенд, поэтому сессия и cookie работают как в production. Без `DATABASE_URL` данные лежат в `.data/workspace.json`, `make reset-data` их сбрасывает.

В docker, вместе с PostgreSQL:

```bash
make env    # .env из .env.example + генерация секретов, один раз
make up     # postgres → миграции → api → web
make seed   # демо-данные, если нужны
make logs
make down
```

`make env` обязателен: рабочих значений секретов в репозитории нет, и `make up` не станет подниматься без них. Он копирует `.env.example` и сразу генерирует `ADMIN_PASSWORD`, `SURVEY_RESPONSE_SECRET`, `DEMO_PASSWORD` и `POSTGRES_PASSWORD`. Повторный запуск существующие значения не трогает.

Порты пробрасываются те же, PostgreSQL на `5433` (5432 на машине разработчика обычно уже занят). `make down-v` дополнительно удаляет volume с данными, то есть вся локальная база пропадает; для смены пароля Postgres он не подходит, см. [runbook](docs/runbook.md#смена-пароля-postgres-в-compose-стеке-без-потери-данных). `make up-prod` поднимает прод-подобный стек из runtime-образа на `http://127.0.0.1:8080` — тот же образ, который пойдет в registry.

### Секреты

```bash
make secrets        # заполнить пустые, существующие не трогать
make secrets-force  # перегенерировать всё
make secrets-check  # найти пустые, слабые и совпадающие значения
make admin-password # сменить пароль админа в работающей базе, без рестарта
```

Пароля администратора по умолчанию не существует. Вне `local` его отсутствие — отказ старта. В `local` он генерируется при первом запуске, печатается один раз и дописывается в `.env`.

Смена `ADMIN_PASSWORD` в окружении применяется при рестарте и сбрасывает активные сессии администратора. Если переменная не менялась, база остаётся авторитетной — ротация через `make admin-password` не откатывается ближайшим рестартом.

## Тесты

Четыре слоя, у каждого свой запуск.

| Что | Команда | Что нужно |
|---|---|---|
| Юнит-тесты (чистые функции: `lib/`, `src/csv.js`) | `npm run test:unit` | ничего: ни сети, ни базы |
| Интеграционные (репозитории на настоящем PostgreSQL) | `npm run test:integration` | `TEST_DATABASE_URL` |
| API-тесты защиты (`tests/api`) | `npm run test:api` | запущенный сервер, `BASE_URL`, `ADMIN_PASSWORD` |
| UI-сценарий конфликта (`tests/ui/conflict.spec.js`) | `npm run test:conflict` | запущенный сервер, браузер playwright |
| Smoke и UI-аудит (`tests/smoke.spec.js`, `tests/ui-audit.spec.js`) | `npm run test:smoke`, `npm run test:ui` | запущенный сервер, браузер playwright |

Интеграционные тесты стирают таблицы (`truncate`), поэтому работают только с базой, в имени которой есть `test`: иначе тест отказывается даже подключаться. Базу надо создать и довести миграциями до актуальной схемы:

```bash
createdb team_health_test
DATABASE_URL=postgres://user:pass@127.0.0.1:5432/team_health_test node scripts/migrate.mjs up
TEST_DATABASE_URL=postgres://user:pass@127.0.0.1:5432/team_health_test npm run test:integration
```

Playwright-тесты читают `BASE_URL` (по умолчанию `http://127.0.0.1:4173`), `ADMIN_USERNAME` и `ADMIN_PASSWORD`; пароля по умолчанию у них нет, без него тесты не стартуют. Они делят одно состояние сервера (общая база, `/api/reset`), поэтому идут последовательно и должны идти против сервера с `APP_ENV=local`: в production `/api/reset` закрыт.

Всё вместе в docker (основной способ):

```bash
make test-docker
```

Поднимает отдельные PostgreSQL и сервер, прогоняет миграции с нуля, сидинг, затем весь playwright (`npx playwright test`: smoke, UI-аудит, `tests/api`, `tests/ui`) в контейнере и убирает за собой. Юнит- и интеграционные тесты этот профиль не запускает. Dev-стек и его данные при этом не трогаются, тестовая база живёт в tmpfs.

На хосте, против уже запущенного приложения:

```bash
make test-install   # браузер для playwright, один раз
make build && make start
make test
```

CI (`.github/workflows/ci.yml`) на каждый PR и push в `main` запускает пять заданий: проверка секретов (gitleaks и поиск скомпрометированных значений в дереве), сборка, юнит-тесты, миграции (с нуля, соответствие `db/schema.sql`, down/up последней миграции, baseline + up, сидинг, интеграционные тесты) и E2E (`make test-docker`).

## Production build

```bash
npm run build
npm run start
```

`server.js` отдает собранный `dist`, API авторизации и рабочие данные. В production данные хранятся в PostgreSQL через `DATABASE_URL`.

### Переменные окружения

Шаблон — `.env.example`. Часть переменных ниже в нём не перечислена; здесь список полный, по коду `server.js` и `scripts/`.

Режим и сеть:

- `APP_ENV` со значениями `local` и `production`; включает все production-защиты сразу. Любое другое значение — отказ старта. Если не задан, определяется автоматически: `production` при наличии `RAILWAY_ENVIRONMENT`, иначе `local`. Тот же вывод делают скрипты `migrate`, `seed` (общий код `scripts/lib/env.mjs`), так что на Railway переменную задавать не нужно. Образ из `Dockerfile` (стадия `runtime`) уже содержит `APP_ENV=production`;
- `RAILWAY_ENVIRONMENT` ставит сама платформа Railway; руками её не задают;
- `PORT`, который задает Railway (по умолчанию 4173);
- `TRUST_PROXY=1` — доверять `X-Forwarded-For` при ограничении попыток входа. В production включено само, вручную нужно только если перед приложением с `APP_ENV=local` стоит прокси;
- `TRUSTED_PROXY_HOPS` — сколько доверенных прокси стоит перед приложением, целое >= 1, по умолчанию 1. Подробности в «Безопасность доступа»;
- `SHUTDOWN_TIMEOUT_MS` — общий бюджет graceful shutdown, по умолчанию 10000;
- `SHUTDOWN_DRAIN_MS` — пауза между «`/readyz` отвечает 503» и закрытием слушателя, чтобы балансировщик успел вывести инстанс из ротации. По умолчанию 3000 в production и 0 в local; входит в `SHUTDOWN_TIMEOUT_MS`, а не прибавляется к нему, и не превышает его половины.

Хранилище:

- `DATABASE_URL` для PostgreSQL;
- `DATABASE_SSL` со значениями `require`, `verify-full` или `disable`; без переменной SSL берется из строки подключения. Её же учитывают `migrate`, `admin-password` и `backup`;
- `DATABASE_POOL_MAX` — размер пула соединений, по умолчанию 10;
- `DATA_DIR` только как локальный fallback без PostgreSQL;
- `ALLOW_FILE_STORAGE=1` только если сознательно нужен production-запуск без PostgreSQL; по умолчанию Railway без `DATABASE_URL` не стартует, чтобы не потерять данные на ephemeral FS;
- `WORKSPACE_SCOPED_READ=0` возвращает чтение всей базы на каждый запрос (рычаг отката скоупленного чтения). В норме не трогать.

Учётные записи и секреты:

- `ADMIN_USERNAME` (по умолчанию `admin`) и `ADMIN_PASSWORD` для учётной записи администратора. Пароля по умолчанию нет ни в одном окружении: вне `local` старт без него невозможен, пароль короче 12 символов или из блок-листа скомпрометированных — тоже.
- `ADMIN_NAME` — отображаемое имя администратора, по умолчанию «Администратор».
- `DEMO_USERNAME` и `DEMO_PASSWORD` для демо 1:1; учётка создаётся сидингом (в file-режиме — самим приложением), а не при старте с PostgreSQL. Если `DEMO_PASSWORD` не задан, используется `demo`.
- `SURVEY_RESPONSE_SECRET` для стабильного server-side hash анонимных ответов. Фолбэка на `ADMIN_PASSWORD` больше нет: список `userId` администратору доступен, и общий секрет позволял сопоставить анонимный ответ с автором. Вне `local` обязателен и не может совпадать с `ADMIN_PASSWORD`.
- `ENABLE_DEMO_RESET=1` включает опасный endpoint `/api/reset` в production (в том числе на Railway); без флага сброс демо-данных доступен только в `local`.

Только для docker compose и разработки (`.env.example`): `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT`, `API_PORT`, `WEB_PORT`, `PROD_PORT`, `PROD_ADMIN_PASSWORD` (пароль админа для профиля `prod`), `VITE_API_TARGET` (куда vite проксирует `/api`).

Для `scripts/backup.mjs restore-check`: `RESTORE_CHECK_DATABASE_URL` (запасной путь вместо `--into`, чтобы пароль не попадал в аргументы процесса). Для интеграционных тестов: `TEST_DATABASE_URL`; для API- и UI-тестов: `BASE_URL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `DEMO_USERNAME`, `DEMO_PASSWORD`.

## Railway

В репозитории уже есть `railway.json`:

- build command: `npm ci --include=dev && npm run build`;
- start command: `npm run migrate && npm run start`;
- healthcheck: `/readyz` (таймаут 30 с);
- перезапуск `ON_FAILURE`, не более 10 раз.

Миграции идут перед стартом приложения при каждом запуске контейнера. Реплика на Railway одна, а advisory-лок в `scripts/migrate.mjs` закрывает случай, когда старый и новый контейнер накладываются: второй процесс видит занятый лок и выходит с кодом 1, ничего не применив (код 0 означал бы «схема актуальна», и деплой пошёл бы дальше). `npm run migrate && npm run start` в этом случае не запускает приложение, а Railway повторяет старт; после завершения первого процесса повторный `migrate` видит, что применять нечего, и проходит.

Если в вашем проекте Railway доступен pre-deploy command, миграции лучше перенести туда: тогда падение миграции не будет выглядеть как падение приложения.

**Существующая база.** Один раз, до первого деплоя с этими изменениями, сначала резервная копия, затем baseline:

```bash
DATABASE_URL=... node scripts/backup.mjs dump
DATABASE_URL=... npm run migrate:baseline
DATABASE_URL=... npm run migrate
```

Команда `baseline` отмечает `0001`–`0016` применёнными, не выполняя их, — схему, которую создавал старый код, пересоздавать не нужно. Автоматически baseline не делается намеренно: это разовая операция над живой базой. Если запустить `migrate` на такой базе раньше, команда остановится с подсказкой и ничего не применит. Пошаговая процедура для Railway (включая PowerShell) — в [runbook](docs/runbook.md#первый-деплой-на-существующую-живую-базу-railway), подробности про baseline — в `migrations/README.md`.

## Проверки состояния

- `GET /healthz` отвечает `200`, пока жив процесс: liveness. Не зависит от базы и от остановки.
- `GET /readyz` проверяет хранилище (`SELECT 1` для PostgreSQL, наличие файла для file-режима) и отвечает `503`, если запрос к хранилищу не прошёл. После `SIGTERM` он сразу отвечает `503 {"status":"shutting_down"}`, пока сервер ждёт (`SHUTDOWN_DRAIN_MS`) и дорабатывает активные запросы: так балансировщик выводит инстанс из ротации раньше, чем сервер закроет порт.
- `GET /metrics` отдаёт состояние пула соединений, счётчики записей и чтений и счётчик конфликтов версий. Секретов там нет, но и авторизации тоже — в k8s его стоит закрыть NetworkPolicy, а не выставлять наружу; на Railway с публичным доменом он доступен всем.

**Старая схема.** Приложение при старте проверяет последнюю запись журнала `pgmigrations`. Если база старше кода (или журнала нет вовсе), процесс не стартует: завершается с ошибкой «База на миграции …, коду нужна …» или «Схема не инициализирована» и сообщением, что выполнить. `/readyz` в этом случае не отвечает вообще (порт не открыт), а `503` не отдаёт. Причину ищут в логах контейнера. База новее кода — штатная ситуация при rolling update: приложение пишет предупреждение и стартует. Ожидаемую версию схемы показывает `/metrics` (поле `schema`).

Очередь в пуле (`pool.waiting`), отличная от нуля, означает, что узким местом стал пул, а не база. Счётчик `versionConflicts` — прямой индикатор того, насколько часто пользователи реально конфликтуют при одновременном редактировании. `readRows` делённое на число запросов показывает, сколько строк приложение поднимает из базы на один ответ: если оно растёт вместе с размером базы у сотрудника, который видит одного человека, значит скоуп где-то потерялся. Счётчики живут в памяти процесса и обнуляются при рестарте.

Все три эндпоинта не требуют авторизации и не кешируются. По `SIGTERM` и `SIGINT` сервер перестает принимать соединения, дожидается активных запросов, закрывает пул PostgreSQL и выходит.

Для надежного хранения нужен Railway PostgreSQL. Добавление через CLI:

```bash
railway add --database postgres
railway variable set DATABASE_URL='${{Postgres.DATABASE_URL}}'
```

Деплой через CLI:

```bash
railway login
railway init
railway up
```

После деплоя в Railway нужно сгенерировать публичный домен в настройках Networking.

## Безопасность доступа

- `/api/workspace` возвращает `401` без активной сессии; неавторизованный запрос не читает базу.
- Пароли хэшируются через Node.js `scrypt`.
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, в production также `Secure`. Вход удаляет остальные сессии этого пользователя: одна активная сессия на логин ([ADR 0002](docs/adr/0002-single-session-per-user.md)).
- В production каждый ответ несёт `Strict-Transport-Security: max-age=15552000` (полгода, без `includeSubDomains` и `preload`). В `local` заголовка нет.
- Смена своего пароля (`POST /api/me/password`) требует `currentPassword`. Неверный или пустой — `400 «Неверный текущий пароль»` (не 401: клиент разлогинивает по 401). Попытки идут в тот же лимитер, что и вход. Остальные сессии пользователя после смены гаснут, текущая остаётся. Пароль системного админа этим способом не меняется (им управляет `ADMIN_PASSWORD`), пароль демо-учётки тоже (`403`, им управляет `DEMO_PASSWORD`).
- Ограничение попыток входа: 8 неудачных попыток на пару «адрес:логин» и 30 на адрес за 15 минут. Глобального счётчика по одному логину нет намеренно: иначе любой мог бы заблокировать чужую учётку, набирая её логин. Счётчики в памяти процесса, ограничены по числу и длине ключей.
- Адрес клиента за прокси: при `APP_ENV=production` или `TRUST_PROXY=1` берётся из `X-Forwarded-For` справа, позиции `TRUSTED_PROXY_HOPS` (по умолчанию 1, один балансировщик, как на Railway). Левую часть заголовка клиент подделывает, поэтому она не используется. Если в заголовке меньше записей, чем указано прокси, или значение не IP, берётся адрес сокета. Если перед приложением два и более прокси (например, CDN и балансировщик), нужно поставить `TRUSTED_PROXY_HOPS=2` и т. д.: при заниженном значении за адрес клиента принимается адрес прокси, и лимит делится между всеми пользователями ([ADR 0003](docs/adr/0003-trusted-proxy.md)).
- Администратор видит команду, приватные заметки и список логинов. Лид видит приватные заметки, которые написал сам, и старые заметки без автора (подробнее в разделе «Приватность и роли»).
- Опросы scoped по владельцу/команде; лиды не могут удалять или копировать чужие опросы по прямому id.
- Анонимные агрегаты скрыты до порога ответов (не ниже 3, отдельно по каждому вопросу), а повторный ответ участника обновляет предыдущий через server-side hash.
- Токены сессий в базе хранятся хэшем (sha256), в cookie лежит сырой токен ([ADR 0006](docs/adr/0006-session-tokens-hashed.md)).
- Учётная запись администратора (`ADMIN_USERNAME`) защищена от удаления из интерфейса.
- Участник не получает список пользователей, приватные заметки и данные других участников.
- `/api/reset` в production отключён без явного `ENABLE_DEMO_RESET=1`, чтобы админская кнопка не могла случайно стереть рабочую команду.

## Приватность и роли

Полное обоснование и остаточные риски - в [ADR 0005](docs/adr/0005-privacy-model.md). Все ограничения применяет сервер, а не интерфейс.

- **Участник** (и демо-пользователь) видит только своё рабочее пространство. Оценочные тексты лида о нём (`performanceNarrative`, `growthNarrative`) в ответах API вырезаются; из оценок компетенций он видит только проверенные (`validated`). Поле `managerFocus` остаётся, оно показывается в общем виде встречи.
- **Лид** видит свою команду, все оценки компетенций и оценочные тексты. Приватные заметки привязаны к автору: лид видит свои заметки и старые заметки без автора (они считаются общими для лидов скоупа); чужую заметку удалить нельзя, ответ `404`.
- **Администратор платформы** видит все заметки своего скоупа, управляет логинами и читает журнал аудита.
- **Анонимные опросы.** Порог ответов не ниже 3 (по умолчанию 3, максимум 10). Агрегат каждого вопроса показывается только если на этот вопрос ответило не меньше порога респондентов, иначе вместо него `{ count, hidden: true, minResponses }`. Результаты обновляются в реальном времени: разностная атака между просмотрами осознанно не закрыта и записана как остаточный риск.
- **Опрос удалённого лида** доступен только администратору платформы, а не всей организации. Постоянное удаление человека удаляет и его именные ответы на опросы.
- **Журнал аудита.** Создание и удаление учёток, смена ролей, сброс и смена паролей, архивация, восстановление и постоянное удаление людей, удаление опросов и заметок пишутся в таблицу `audit_log`; пароли и тексты заметок не пишутся. Читает только администратор платформы: `GET /api/audit-log?limit=100&before=<id>` (остальным `403`). В file-режиме журнала нет, срока хранения нет ([runbook](docs/runbook.md#журнал-аудита)).
- **Сессии.** В базе хранится sha256 от токена, сырой токен лежит только в cookie. После выкладки этой версии все входят заново.

## Запись и конфликты

Клиент по-прежнему отправляет рабочее пространство целиком (`POST /api/workspace`), но сервер больше не трактует тело как «истину в последней инстанции». Два механизма, оба описаны в [ADR 0001](docs/adr/0001-write-model.md):

- **Запись разностью.** При чтении из PostgreSQL сервер запоминает базовое состояние строк (`snapshotRows` в `db/repositories/workspace.js`). При записи `syncWorkspace` пишет только новые и изменённые строки и удаляет только те, что были в базовом состоянии и исчезли. Строка, которую параллельно создал другой пользователь, а также свежая сессия или новый пароль в таблицы не затираются, потому что запись их просто не касается. Без базового состояния (старые вызовы) поведение прежнее: полный снимок.
- **`knownIds`.** Тело запроса может содержать `knownIds = { cards, actions, goals, lprs, competencyAssessments }` — списки id, которые клиент видел (получил с сервера или сам создал и успешно сохранил). Строка из базы, которой нет в теле, удаляется только если её id есть в `knownIds` своей таблицы; если id там нет, клиент её не видел, и строка сохраняется. Если `knownIds` не прислан или поле таблицы не массив, действует прежняя семантика «нет в теле — удалено» (старые клиенты, API-тесты). Лимиты: до 20000 id на таблицу, id длиной не более 200 символов. Правило действует для админа и лида по всем пяти таблицам, для сотрудника по карточкам, шагам, целям и ЛПР (оценки компетенций сотрудник не записывает).
- **Оптимистичная блокировка.** Для карточек, договорённостей, целей и ЛПР версия строки — её `updatedAt`. Сохранение строки, которую успели изменить, возвращает `409` с `conflicts` (таблица и id) и актуальным `workspace`; счётчик `versionConflicts` в `/metrics` растёт. Проверяются только строки, которые это сохранение реально меняет. Интерфейс при `409` показывает баннер с выбором «загрузить актуальные данные» или «перезаписать моими» и не повторяет сохранение бесконечно; прочие `4xx` останавливают повтор, сетевые ошибки и `5xx` повторяются с нарастающей паузой до 30 с.

Гонки двух людей над одной и той же строкой по-прежнему решает блокировка и баннер конфликта, а не слияние полей.

## База данных

Схемой управляют миграции в `migrations/`. Приложение DDL не выполняет — при старте оно только проверяет, что база не старше кода, и если старше, отказывается стартовать (см. «Старая схема» выше).

```bash
make migrate            # применить всё, что не применено
make migrate-status     # что применено, что ожидает
make migrate-new name=add_teams
make migrate-down       # откатить одну последнюю, только local
make db-schema          # обновить снимок db/schema.sql
make db-drift           # сравнить снимок с реальной схемой
make db-dump            # бэкап локальной базы из контейнера в backups/
make db-restore file=backups/....dump
```

Защиты скриптов определяют окружение так же, как сервер (`scripts/lib/env.mjs`: `APP_ENV`, а без него `RAILWAY_ENVIRONMENT` означает production):

- `migrate down` и `migrate redo` вне `local` отказываются работать. Откат схемы на проде — восстановление из бэкапа или новая миграция вперёд;
- `seed` в production запрещён безусловно, `--force` не помогает; в окружении, отличном от `local` и `production`, нужен явный `--force`.

Защита смотрит на переменные окружения процесса, а не на адрес базы: запуск `migrate down` или `seed` с ноутбука против боевого `DATABASE_URL` без `APP_ENV=production` защиту не включает. Работая с боевой базой с локальной машины, задавайте `APP_ENV=production` в том же окне ([runbook](docs/runbook.md)).

### Резервные копии

```bash
node scripts/backup.mjs dump                                 # дамп DATABASE_URL в backups/
node scripts/backup.mjs verify backups/<файл>.dump           # файл читается, ключевые таблицы на месте
node scripts/backup.mjs restore-check backups/<файл>.dump --into postgresql://.../team_health_test
```

`dump` пишет `pg_dump -Fc` во временный файл и переименовывает его только при успехе, пустой дамп не считается бэкапом. `verify` проверяет оглавление (`pg_restore --list`). `restore-check` восстанавливает дамп в отдельную тестовую базу (имя базы обязано содержать `test`, с базой из `DATABASE_URL` команда не работает) и сравнивает число строк ключевых таблиц (`users`, `people`, `cards`, `actions`, `goals`, `pgmigrations`) с содержимым дампа; перед восстановлением объекты в целевой базе удаляются. Нужны `pg_dump` и `pg_restore` в `PATH`, версии не ниже серверной. Дамп содержит хэши паролей и ответы опросов: храните его как секрет. Расписания и хранения вне хоста в репозитории нет. Порядок действий и проверка восстановления — в [runbook](docs/runbook.md). `make db-dump` по-прежнему снимает копию только локальной базы из контейнера `db`.

### Эксплуатация

```bash
make db-bloat           # сколько мёртвых версий строк накопилось
make db-vacuum          # разовая чистка, только в окне обслуживания
```

Раньше любая мутация переписывала шестнадцать таблиц целиком, и мёртвых версий строк в базе накапливалось в три-пять раз больше живых. После перехода на точечные записи имеет смысл один раз прибраться (`make db-vacuum`) и посмотреть, нужен ли более агрессивный autovacuum — скорее всего нет, потому что churn был следствием полной перезаписи.

`db/schema.sql` — снимок актуальной схемы, который коммитится: схема читается одним файлом, без склеивания двух десятков миграций в голове. Правила написания миграций, политика отката и чек-лист ревьюера — в `migrations/README.md`.

Демо-данные не заливаются при старте с PostgreSQL. `make seed` — отдельная команда (вне `local` — только с `--force`, в production запрещена). Сам старт приложения демо-данные не создаёт. Оговорка: `normalizeDb` в `server.js` пока достраивает демо-фикстуры при чтении и записи (находка arch-5 аудита, см. «Известные ограничения» в [handbook](docs/product-handbook.md#14-известные-ограничения)), так что полностью «чистой» от демо-данных боевую базу считать нельзя.

### Слой `db/repositories`

Запись в PostgreSQL вынесена из `server.js`; чтение рабочего пространства (`readDb`, `readDbForUser`) остаётся в `server.js`.

- `tables.js` — описание таблиц: колонки, типы, функции `value()` (как поле объекта приложения превращается в значение колонки) и ключи. Один источник для upsert и для расчёта подписей строк.
- `sync.js` — общие операции над таблицей: upsert с условием «строка действительно изменилась» (без него триггер `updated_at` ломает оптимистичную блокировку), удаление по ключам, расчёт разницы с базовым состоянием, поиск устаревших версий.
- `workspace.js` — `syncWorkspace` (запись всего рабочего пространства в одной транзакции, полным снимком или разностью), `snapshotRows` (базовое состояние), `VersionConflictError`, поддержка таблицы `teams`.
- `auth.js` — сессии и учётные записи: поиск сессии одним запросом, `createSession`, удаление сессий, смена пароля и имени.

### Таблицы

Источник правды — `db/schema.sql`. Кратко:

- `people`, `users`, `sessions`, `teams`;
- `cards`, `actions`, `lprs`, `goals`, `competency_assessments`;
- `prep` — чек-лист подготовки по человеку, `meeting_drafts` — живой протокол встречи, `meeting_log` — история итогов;
- `notes` — текущий текст приватной заметки лида о человеке (одна строка на человека); история заметок — в `manager_notes`;
- `pulse_history` — точки пульса по дням, а `pulse` — **представление** (view) над ней: текущий пульс человека — это его последняя точка (миграция `0026`). Писать в `pulse` как в таблицу нельзя;
- `surveys`, `survey_responses`;
- `oncall_load` — необязательная таблица Ops/on-call сценария;
- `teams` — команда как объект. Заполняется из связей `users.lead_user_id` и `team_label` при каждой записи с учётными данными; колонка `team_id` у `users` и `people` пока служебная, скоуп доступа по ней не читается;
- `app_meta` — служебные записи приложения (отпечатки секретов, версия секрета опросов);
- `pgmigrations` — журнал миграций (создаёт `node-pg-migrate`, в `db/schema.sql` не входит).

В таблицах есть foreign keys, check constraints и индексы для пользователей, сессий, тем, целей, опросов и следующих шагов.

## Продуктовые принципы

- 1:1 не должен быть статус-апдейтом: встреча принадлежит участнику, а лид приходит подготовленным.
- Повестка общая и живет между встречами, чтобы вопросы добавлялись в моменте.
- В конце встречи должны появляться конкретные следующие шаги.
- Разговор должен регулярно покрывать wellbeing, alignment, progress, relationships и career growth.
- Базовый продукт не привязан к одной функции: Product, Engineering, Support, Sales, Operations и People-команды должны узнавать свои процессы.
- Доменные сигналы вроде on-call, инцидентов или клиентских эскалаций подключаются как шаблоны, а не определяют позиционирование всей платформы.
