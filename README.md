# Team Health 1:1

[![Ask DeepWiki](https://deepwiki.com/badge.svg)](https://deepwiki.com/fadeinflames/team-health)

Платформа для регулярной управленческой работы с командой: 1:1, развитие, цели, обратная связь, командный пульс, договоренности, матрица компетенций и следующие шаги живут в одном процессе, а не расползаются по заметкам, чатам и таблицам.

## Что уже работает

- серверная авторизация через httpOnly cookie;
- локальный seed-админ: `mgusev` / `passwb121`;
- локальный демо-вход: `demo` / `demo` с готовым универсальным 1:1;
- постоянное боковое меню: Главная, 1:1 встречи, ЛПР, Цели, Опросы, Отчёты, Команда, Админка, Настройки;
- единый раздел администратора “Команда” с профилями участников 1:1, состоянием команды и доступами;
- добавление участников администратором и тимлидом в рамках своей команды;
- создание логинов участников с главной, из “Команды” и из админского раздела;
- доступы рабочей команды внутри “Команда”: обновление пароля и удаление не-админских логинов;
- локальный или явно разрешённый сброс демо-данных без разлогина админа;
- серверная изоляция данных: участник получает только свой профиль, темы 1:1, пульс, чек-лист и следующие шаги;
- выбор участника и отдельное рабочее пространство 1:1;
- темы повестки от участника и лида;
- фильтры по открытым темам, автору, пульсу и росту;
- интерактивный пульс 1:1: энергия, нагрузка, ясность, доверие;
- живой общий протокол встречи, который сохраняется между вкладками и попадает в итоги 1:1;
- чек-лист подготовки за 24 часа до встречи;
- приватные заметки лида;
- следующие шаги с владельцами и сроками;
- генерация кратких итогов встречи;
- ЛПР: планы развития, которые связывают темы 1:1 с целями;
- цели с прогрессом, статусом, сроком и связью с ЛПР;
- опросы команды: шаблоны, конструктор, ответы, scoped-доступ, порог анонимности, агрегаты и CSV export;
- отчёты по пульсу, темам, приоритетам, целям, действиям, балансу авторства повестки и компетенциям;
- отчёты кейс-интервью: структурированные компетенции, грейд, доказательства, рекомендации, командная матрица, CSV export и импорт зон роста в ЛПР;
- ролевая модель: админ платформы, тимлид, участник команды;
- доменные шаблоны, включая optional Ops/on-call сценарий для команд с дежурствами;
- сохранение состояния на сервере: PostgreSQL в production, локальный file fallback без `DATABASE_URL`.

## Локальный запуск

```bash
npm install
npm run build
npm run start
```

Приложение откроется на `http://127.0.0.1:4173`.

## Разработка

`make help` показывает все цели. Два равноценных режима, в обоих правки применяются сразу: бэкенд перезапускает `node --watch`, фронтенд обновляет vite HMR.

На хосте:

```bash
make install
make dev
```

UI на `http://127.0.0.1:5173`, API на `http://127.0.0.1:4173`. Vite проксирует `/api` на бэкенд, поэтому сессия и cookie работают как в production. Без `DATABASE_URL` данные лежат в `.data/workspace.json`, `make reset-data` их сбрасывает.

В docker, вместе с PostgreSQL:

```bash
make env    # .env из .env.example, опционально
make up
make logs
make down
```

Порты пробрасываются те же, PostgreSQL на `5433` (5432 на машине разработчика обычно уже занят). `make down-v` дополнительно удаляет volume с данными. `make up-prod` поднимает прод-подобный стек из runtime-образа на `http://127.0.0.1:8080` — тот же образ, который пойдет в registry.

## Production build

```bash
npm run build
npm run start
```

`server.js` отдает собранный `dist`, API авторизации и рабочие данные. В production данные хранятся в PostgreSQL через `DATABASE_URL`.

Сервер использует:

- `APP_ENV` со значениями `local` и `production`; включает все production-защиты сразу. Если не задан, определяется автоматически: `production` при наличии `RAILWAY_ENVIRONMENT`, иначе `local`;
- `PORT`, который задает Railway;
- `DATABASE_URL` для PostgreSQL;
- `DATABASE_SSL` со значениями `require`, `verify-full` или `disable`; без переменной SSL берется из строки подключения;
- `SHUTDOWN_TIMEOUT_MS` для graceful shutdown, по умолчанию 10000;
- `DATA_DIR` только как локальный fallback без PostgreSQL;
- `ADMIN_USERNAME` и `ADMIN_PASSWORD` для seed-админа при первом запуске; на Railway `ADMIN_PASSWORD` обязателен и не может оставаться значением по умолчанию.
- `DEMO_USERNAME` и `DEMO_PASSWORD` для демо 1:1.
- `SURVEY_RESPONSE_SECRET` для стабильного server-side hash анонимных ответов; если не задан, используется `ADMIN_PASSWORD`.
- `ALLOW_FILE_STORAGE=1` только если сознательно нужен production-запуск без PostgreSQL; по умолчанию Railway без `DATABASE_URL` не стартует, чтобы не потерять данные на ephemeral FS.
- `ENABLE_DEMO_RESET=1` включает опасный endpoint `/api/reset` на Railway; без флага сброс демо-данных доступен только локально.

## Railway

В репозитории уже есть `railway.json`:

- build command: `npm run build`;
- start command: `npm run start`;
- healthcheck: `/healthz`.

## Проверки состояния

- `GET /healthz` отвечает `200`, пока жив процесс: liveness.
- `GET /readyz` дополнительно проверяет хранилище (`SELECT 1` для PostgreSQL, наличие файла для file-режима) и отвечает `503`, если оно недоступно: readiness.

Оба эндпоинта не требуют авторизации и не кешируются. По `SIGTERM` и `SIGINT` сервер перестает принимать соединения, дожидается активных запросов, закрывает пул PostgreSQL и выходит.

Для надежного хранения нужен Railway PostgreSQL. Добавление через CLI:

```bash
railway add --database postgres
railway variable set DATABASE_URL='${{Postgres.DATABASE_URL}}'
```

Деплой через CLI:

```bash
railway login
railway init
railway up
```

После деплоя в Railway нужно сгенерировать публичный домен в настройках Networking.

## Безопасность доступа

- `/api/workspace` возвращает `401` без активной сессии.
- Пароли хэшируются через Node.js `scrypt`.
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, на Railway также `Secure`.
- Администратор видит команду, приватные заметки и список логинов.
- Опросы scoped по владельцу/команде; лиды не могут удалять или копировать чужие опросы по прямому id.
- Анонимные агрегаты скрыты до минимального порога ответов, а повторный ответ участника обновляет предыдущий через server-side hash.
- Seed-аккаунты `mgusev` и `demo` защищены от удаления из интерфейса.
- Участник не получает список пользователей, приватные заметки и данные других участников.
- `/api/reset` в production отключён без явного `ENABLE_DEMO_RESET=1`, чтобы админская кнопка не могла случайно стереть рабочую команду.

## Продуктовые принципы

- 1:1 не должен быть статус-апдейтом: встреча принадлежит участнику, а лид приходит подготовленным.
- Повестка общая и живет между встречами, чтобы вопросы добавлялись в моменте.
- В конце встречи должны появляться конкретные следующие шаги.
- Разговор должен регулярно покрывать wellbeing, alignment, progress, relationships и career growth.
- Базовый продукт не привязан к одной функции: Product, Engineering, Support, Sales, Operations и People-команды должны узнавать свои процессы.
- Доменные сигналы вроде on-call, инцидентов или клиентских эскалаций подключаются как шаблоны, а не определяют позиционирование всей платформы.
