# Team Health 1:1

Платформа для регулярной управленческой работы с командой: 1:1, развитие, цели, обратная связь, командный пульс, договоренности и следующие шаги живут в одном процессе, а не расползаются по заметкам, чатам и таблицам.

## Что уже работает

- серверная авторизация через httpOnly cookie;
- seed-админ: `mgusev` / `passwb121`;
- демо-вход: `demo` / `demo` с готовым универсальным 1:1;
- постоянное боковое меню: Главная, 1:1 встречи, ЛПР, Цели, Опросы, Отчёты, Команда, Админка, Настройки;
- единый раздел администратора “Команда” с профилями участников 1:1, состоянием команды и доступами;
- добавление участников администратором;
- создание логинов участников администратором;
- доступы рабочей команды внутри “Команда”: обновление пароля и удаление не-админских логинов;
- сброс демо-данных без разлогина админа;
- серверная изоляция данных: участник получает только свой профиль, темы 1:1, пульс, чек-лист и следующие шаги;
- выбор участника и отдельное рабочее пространство 1:1;
- темы повестки от участника и лида;
- фильтры по открытым темам, автору, пульсу и росту;
- интерактивный пульс 1:1: энергия, нагрузка, ясность, доверие;
- чек-лист подготовки за 24 часа до встречи;
- приватные заметки лида;
- следующие шаги с владельцами и сроками;
- генерация кратких итогов встречи;
- ЛПР: планы развития, которые связывают темы 1:1 с целями;
- цели с прогрессом, статусом, сроком и связью с ЛПР;
- опросы команды: шаблоны, конструктор, ответы, агрегаты и CSV export;
- отчёты по пульсу, темам, приоритетам, целям, действиям и балансу авторства повестки;
- ролевая модель: админ платформы, тимлид, участник команды;
- доменные шаблоны, включая optional Ops/on-call сценарий для команд с дежурствами;
- сохранение состояния на сервере: PostgreSQL в production, локальный file fallback без `DATABASE_URL`.

## Локальный запуск

```bash
npm install
npm run build
npm run start
```

Приложение откроется на `http://127.0.0.1:4173`.

## Production build

```bash
npm run build
npm run start
```

`server.js` отдает собранный `dist`, API авторизации и рабочие данные. В production данные хранятся в PostgreSQL через `DATABASE_URL`.

Сервер использует:

- `PORT`, который задает Railway;
- `DATABASE_URL` для PostgreSQL;
- `DATA_DIR` только как локальный fallback без PostgreSQL;
- `ADMIN_USERNAME` и `ADMIN_PASSWORD` для seed-админа при первом запуске; на Railway `ADMIN_PASSWORD` обязателен и не может оставаться значением по умолчанию.
- `DEMO_USERNAME` и `DEMO_PASSWORD` для демо 1:1.

## Railway

В репозитории уже есть `railway.json`:

- build command: `npm run build`;
- start command: `npm run start`;
- healthcheck: `/`.

Для надежного хранения нужен Railway PostgreSQL. Добавление через CLI:

```bash
railway add --database postgres
railway variable set DATABASE_URL='${{Postgres.DATABASE_URL}}'
```

Деплой через CLI:

```bash
railway login
railway init
railway up
```

После деплоя в Railway нужно сгенерировать публичный домен в настройках Networking.

## Безопасность доступа

- `/api/workspace` возвращает `401` без активной сессии.
- Пароли хэшируются через Node.js `scrypt`.
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, на Railway также `Secure`.
- Администратор видит команду, приватные заметки и список логинов.
- Seed-аккаунты `mgusev` и `demo` защищены от удаления из интерфейса.
- Участник не получает список пользователей, приватные заметки и данные других участников.

## Продуктовые принципы

- 1:1 не должен быть статус-апдейтом: встреча принадлежит участнику, а лид приходит подготовленным.
- Повестка общая и живет между встречами, чтобы вопросы добавлялись в моменте.
- В конце встречи должны появляться конкретные следующие шаги.
- Разговор должен регулярно покрывать wellbeing, alignment, progress, relationships и career growth.
- Базовый продукт не привязан к одной функции: Product, Engineering, Support, Sales, Operations и People-команды должны узнавать свои процессы.
- Доменные сигналы вроде on-call, инцидентов или клиентских эскалаций подключаются как шаблоны, а не определяют позиционирование всей платформы.
